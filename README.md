# Alliance Payments

უძრავი ქონების გაყიდვებისა და გადახდების სამართავი სისტემა: კლიენტები, პროექტები, ბინები, ხელშეკრულებები, გადახდის გრაფიკები და ბანკის გადახდების FIFO განაწილება.

აპლიკაცია აგებულია Laravel 12-ზე, Inertia 2-სა და React 18/TypeScript-ზე. ინტერფეისი და ვალიდაციის შეტყობინებები ქართულადაა, ავტორიზაცია იყენებს web სესიას, დროის სარტყელია `Asia/Tbilisi`.

## დაყენება

მიმდინარე lock ფაილებისთვის საჭიროა **PHP 8.4.1–8.4.x**, Composer 2 და **Node.js 20.x (მინიმუმ 20.19.0) ან 22.12.0+**. ძირითადი ბაზაა PostgreSQL 16+. CLI PHP-ს სჭირდება `pdo_pgsql`, `mbstring` ჩართული `mbregex`-ით (`mb_split`) და `pcntl`; ტესტებისთვის — `pdo_sqlite`. Excel-ის დამატებითი PHP გაფართოებების მოთხოვნებს Composer ამოწმებს. პაკეტების ვერსიები ჩაკეტილია `composer.lock`-სა და `package-lock.json`-ში.

ბრძანებები შეასრულე პროექტის ძირეულ საქაღალდეში, ახალ ასლზე. `.env.example`-ში ენაა `APP_LOCALE=ka`; არსებული `.env`-ის გამოყენებისას ეს მნიშვნელობაც განაახლე.

### 1. დამოკიდებულებები და გარემო

```bash
composer install
composer check-platform-reqs
cp .env.example .env
php artisan key:generate
```

პროექტი იყენებს FrankenPHP-ს **შიგნით ჩაშენებული PHP 8.4-ით**. ჩვეულებრივი CLI PHP-ის შეცვლა ბინარში ჩაშენებულ ვერსიას არ ცვლის. თუ შესაბამისი `./frankenphp` ჯერ არ გაქვს, ერთხელ ააწყვე ოფიციალური წყაროდან. საჭიროა Git, curl და tar; macOS-ზე — Homebrew და Xcode Command Line Tools, Linux/WSL-ზე — C/C++ build ხელსაწყოები.

```bash
bash scripts/install-frankenphp.sh
./frankenphp php-cli -v
```

სკრიპტი აგებს FrankenPHP 1.13.4-ს PHP 8.4-ით და PostgreSQL/XLSX-ისთვის საჭირო გაფართოებებით. პირველი აწყობა დამოკიდებულებებსაც ტვირთავს, ამიტომ დრო და რამდენიმე GB თავისუფალი ადგილი სჭირდება; შესაბამისი ბინარის არსებობისას აწყობა გამოტოვდება. აწყობის ფაილები დროებით საქაღალდეში რჩება, რომლის მდებარეობა იცვლება `FRANKENPHP_BUILD_DIR`-ით. GitHub API-ის ლიმიტის შემთხვევაში გამოიყენე საკუთარი `GITHUB_TOKEN` გარემოს ცვლადი. ბინარი Git-ში არ ინახება. საფუძველი: [FrankenPHP-ის ოფიციალური აწყობა](https://frankenphp.dev/docs/static/).

### 2. დემო ანგარიშები და პაროლები

Seeder-ის გაშვებამდე `.env`-ში მიუთითე სამი განსხვავებული პაროლი. ქვემოთ მოცემული მნიშვნელობები ნიმუშებია — შეცვალე საკუთარი პაროლებით.

```dotenv
DEMO_ADMIN_PASSWORD="replace-with-your-admin-password"
DEMO_EDITOR_PASSWORD="replace-with-your-editor-password"
DEMO_VIEWER_PASSWORD="replace-with-your-viewer-password"
```

| როლი | ელ. ფოსტა | პაროლი | წვდომა |
| --- | --- | --- | --- |
| ადმინისტრატორი | `admin@alliance.ge` | `DEMO_ADMIN_PASSWORD` | ბიზნესფუნქციები, მომხმარებლები და უფლებები |
| რედაქტორი | `editor@alliance.ge` | `DEMO_EDITOR_PASSWORD` | ბიზნესმონაცემების ნახვა და შეცვლა |
| დამთვალიერებელი | `viewer@alliance.ge` | `DEMO_VIEWER_PASSWORD` | მხოლოდ ნახვა |

პაროლები რეპოზიტორიაში არ ინახება. `.env` ლოკალურია; ცარიელი დემო პაროლის შემთხვევაში Seeder ქართულ შეცდომას აბრუნებს. განმეორებითი seed პაროლებს მითითებულ env მნიშვნელობებს უთანხმებს და უკვე Admin-ად დანიშნულ დემო ანგარიშს ამ როლს უნარჩუნებს.

რეგისტრაცია გამორთულია; სხვა ანგარიშებს ადმინისტრატორი ამატებს. უკვე არსებული ანგარიშის Admin როლზე გადასაყვანად გამოიყენე `php artisan users:admin user@alliance.ge` — ჩასვი არსებული ანგარიშის ელ. ფოსტა. ბრძანება ანგარიშს არ ქმნის და პაროლს არ ცვლის; ჯერ როლების Seeder უნდა იყოს გაშვებული.

### 3. PostgreSQL და საწყისი მონაცემები

გაუშვი PostgreSQL და შექმენი `alliance_payments` ბაზა, თუ ჯერ არ არსებობს. მაგალითად, `postgres` როლით:

```bash
createdb --host=127.0.0.1 --port=5432 --username=postgres alliance_payments
```

`.env`-ში მიუთითე შენი PostgreSQL როლი და პაროლი. თუ სხვა როლს იყენებ, შეცვალე `DB_USERNAME` და `createdb` ბრძანების `--username` მნიშვნელობაც:

```dotenv
DB_CONNECTION=pgsql
DB_HOST=127.0.0.1
DB_PORT=5432
DB_DATABASE=alliance_payments
DB_USERNAME=postgres
DB_PASSWORD="your-database-password"
SESSION_DRIVER=database
CACHE_STORE=database
QUEUE_CONNECTION=database
```

```bash
php artisan config:clear
php artisan migrate
php artisan db:seed
```

ახალ ბაზაში Seeder ქმნის 3 დემო ანგარიშს, 6 კლიენტს, 2 პროექტს, 12 ბინას, 7 ხელშეკრულებას, 52 შენატანს, 28 გადახდასა და მათ განაწილებებს. ბიზნესმონაცემები `upsert`-ით ახლდება; კავშირები იძებნება პირადი ნომრით, პროექტი/ქალაქით, ბინის ნომრითა და საბანკო ნომრით.

აპლიკაცია, სესიები, cache და queue PostgreSQL-ს იყენებს. ავტომატური ტესტები კვლავ ცალკე SQLite `:memory:` ბაზაზე სრულდება; მათთვის საჭიროა `pdo_sqlite`.

### 5. Octane და queue worker

`.env.example`-ში უკვე მითითებულია FrankenPHP და ოთხი worker:

```dotenv
OCTANE_SERVER=frankenphp
OCTANE_HOST=127.0.0.1
OCTANE_PORT=8000
OCTANE_WORKERS=4
OCTANE_MAX_REQUESTS=500
```

პირველ ტერმინალში:

```bash
composer start
```

აპლიკაცია გახსენი `http://127.0.0.1:8000`-ზე. Octane ინარჩუნებს Laravel-ის ჩატვირთულ მდგომარეობას worker-ებში; ყოველი მოთხოვნა აპლიკაციას თავიდან აღარ ტვირთავს. გაშვების, reload-ისა და stop-ის საფუძველია [Laravel Octane](https://laravel.com/docs/12.x/octane).

მეორე ტერმინალში:

```bash
php artisan queue:work database --queue=default --sleep=1 --tries=1 --timeout=60
```

Worker ამუშავებს ატვირთულ Excel ფაილებს. მის გარეშე იმპორტი `queued` სტატუსით დარჩება. ფაილები ინახება private დისკზე; `storage:link` ამ იმპორტისთვის საჭირო არ არის.

დეველოპმენტში `composer start`-ისა და ცალკე worker-ის ნაცვლად გამოიყენე:

```bash
composer dev
```

ეს ერთად უშვებს Octane-ს `--watch` რეჟიმში, queue listener-ს, ლოგებსა და Vite-ს. PHP კოდის ცვლილებაზე Octane-ის worker-ები ავტომატურად ახლდება; `chokidar` პროექტის dev დამოკიდებულებაა.

ჩვეულებრივი `composer start`-ისას აპლიკაციის PHP კოდის ან Laravel-ის კონფიგურაციის შეცვლის შემდეგ worker-ები ხელით განაახლე. თუ კონფიგურაცია დაკეშილია, ჯერ `php artisan config:clear` გაუშვი:

```bash
php artisan octane:reload
```

სერვერის პარამეტრების (`OCTANE_WORKERS`, პორტი) ან `php/frankenphp.d/app.ini`-ის შეცვლისას საჭიროა სრული restart: `php artisan octane:stop`, შემდეგ კვლავ `composer start` ან `composer dev`. მდგომარეობას ამოწმებს `php artisan octane:status`. ერთი და იმავე პორტზე გაუშვი ან `composer start`, ან `composer dev`.

ცალკე `queue:work` პროცესში იმპორტის კოდის განახლების შემდეგ გაუშვი `php artisan queue:restart`. ეს მიმდინარე job-ის შემდეგ worker-ს ასრულებს; ხელით გაშვებული worker ზემოთ მოცემული `queue:work` ბრძანებით თავიდან გაუშვი. `composer dev`-ის `queue:listen` თითო job-ზე აპლიკაციას თავიდან ტვირთავს.

ტექნიკურად ჩავარდნილების სიაა `php artisan queue:failed`; მიზეზის გამოსწორების შემდეგ კონკრეტული job გაიმეორე `php artisan queue:retry FAILED_JOB_UUID`-ით, ბოლო არგუმენტის ნაცვლად სიის UUID ჩასვი. ეს იმპორტის ID არ არის. ავარიული შეწყვეტისას იმპორტის ბლოკი 120 წამში იწურება — გამეორებამდე ამ ვადის გასვლას დაელოდე. გაგრძელებას შენარჩუნებული private ფაილი სჭირდება; უკვე დამუშავებული რიგები აღარ მეორდება. `rejected` მონაცემები შეასწორე და ახალი ფაილით ატვირთე.

## რა მუშაობს

- **კლიენტები:** ძიება, პაგინაცია, დამატება/რედაქტირება, ხელშეკრულებებზე გადასვლა და ხელით გადანაწილება. ახალი კლიენტი იმავე პირადი ნომრით ადრე შემოსულ დაუკავშირებელ გადახდებს ავტომატურად იკავშირებს.
- **პროექტები და ბინები:** პროექტის შექმნა, ბინების სია/ფილტრები, თავისუფალი ბინის დამატება და რედაქტირება. გაყიდული ბინის ცვლილება დაბლოკილია.
- **ხელშეკრულებები:** თავისუფალ ბინაზე ხელშეკრულების შექმნა, ზუსტი ჯამის ყოველთვიური გრაფიკი, ბინის `sold` სტატუსი, არსებული ავანსის გადანაწილება და დაფარვის დეტალები.
- **გადახდები:** პირადი ნომრით კლიენტის ამოცნობა, ყველა მის ხელშეკრულებაზე FIFO, ნაწილობრივი დაფარვა, ზედმეტი თანხა და საბანკო ნომრით დუბლიკატის კონტროლი.
- **Excel იმპორტი:** ატვირთვა, ფონური დამუშავება, თითოეული რიგის `imported`/`duplicate`/`rejected` შედეგი, მთვლელები, ქართული შეცდომები და მიმდინარე სტატუსის ავტომატური განახლება.
- **ვადაგადაცილება:** დაუფარავი შენატანები, კლიენტის/პროექტის ფილტრები და ყველა გაფილტრული ჩანაწერის საერთო ჯამი.
- **მიმოხილვა:** დაფარვა, მიღებული/გაუნაწილებელი თანხები, ვადაგადაცილება, არჩეული პერიოდის თვიური გრაფიკი (დაწყების გარეშე — ბოლო 12 თვე), შენატანების სტატუსები, პროექტების ბინები, მოვალეები და უახლოესი შენატანები. ვიჯეტები ნახვის უფლებებითაა დაცული.
- **ავტორიზაცია:** შესვლა/გასვლა, პაროლის დადასტურება და აღდგენა; ეკრანები, შეცდომები და სტანდარტული წერილები ქართულადაა.
- **ადმინისტრირება და პროფილი:** მომხმარებლების დამატება/რედაქტირება/წაშლა, როლები და ინდივიდუალური უფლებები; საკუთარი მონაცემებისა და პაროლის ცვლილება. თვითწაშლა და საკუთარი ადმინისტრაციული უფლებების შეცვლა აკრძალულია.

## Excel-ის ფორმატი

## დამატებით არ განხორციელებულა

სამუშაოში პრიორიტეტი მიენიჭა გადახდების შემოტანას, ზუსტ განაწილებასა და ოპერატორის დასრულებულ სამუშაო ნაკადებს. შემდეგი შესაძლებლობები დამატებით ბიზნესწესებს ან ცალკე დანერგვას მოითხოვს:

- ხელშეკრულების/გრაფიკის ცვლილება, გაუქმება, გადახდის რევერსი და თანხის დაბრუნება — მათი ფინანსური შედეგები ცალკე უნდა განისაზღვროს.
- PDF და Excel ექსპორტი, ცალკე JSON API და Swagger — მიმდინარე ინტერფეისი Inertia-ით მუშაობს.
- ყველა ველის ცვლილების საერთო audit log და soft delete — ამჟამად ინახება განაწილებისა და იმპორტის ისტორია.
- იმპორტის გაგრძელების UI ღილაკი — ტექნიკური ჩავარდნის შემდეგ გაგრძელება ზემოთ აღწერილი CLI გზით მუშაობს.
- Redis/Horizon მონიტორინგი და production განთავსების ავტომატიზაცია — ლოკალურად Octane + FrankenPHP და PostgreSQL მუშაობს; production პროცესების supervision და ინფრასტრუქტურა ცალკე მოსაწყობია.
- ელ. ფოსტის სავალდებულო დადასტურება — Breeze-ის routes არსებობს, მაგრამ User `MustVerifyEmail`-ს არ ახორციელებს. Mailer ლოკალურად `log`-ია; რეალური წერილისთვის საჭიროა mail transport.

## რა შემოწმდა

- სრული ტესტები და production build; დაფარულია თანხა, FIFO, გრაფიკი, ვალიდაცია, უფლებები, დუბლიკატები, rollback და ანგარიშები. ავტორიზაციაში მოწმდება ქართული ტექსტები, შესვლის შეზღუდვა, აღდგენა/დადასტურება და წერილების თარგმანი.
- PostgreSQL-ის იზოლირებულ schema-ში კონკურენტული გაყიდვა და ადმინისტრატორების კონკურენტული დემოტაცია.
- სუფთა ასლში დამოკიდებულებების დაყენება, 18 მიგრაცია, სრული Seeder, build და სამივე დემო ანგარიშით შესვლა.
- ნამდვილი XLSX ატვირთვა და database worker-ით დამუშავება: 123.45 ₾ ზუსტად 12345 თეთრად შეინახა, ჩავარდნილი job არ დარჩა.
- რეფაქტორინგამდე/შემდეგ Query პასუხების დამთხვევა ორ თარიღსა და უფლებების რვა კომბინაციაზე; ბრაუზერში ფილტრები, პაგინაცია, ბმულები, იმპორტის განახლება და Viewer-ის შეზღუდვები.
- მობილური ხედები 320px-დან; ერთგვერდიან სიებში პაგინაცია დამალულია, მრავალგვერდიანში მუშაობს.

## FrankenPHP-ის შემოწმება

შემოწმებაში გამოყენებულია FrankenPHP 1.13.4 / PHP 8.4.27 ZTS / PostgreSQL 16.13, ოთხი worker-ით. ტესტების განყოფილებაში მითითებული სრული suite ჩაშენებულ PHP-ზეც შესრულდა. გადამოწმდა სამივე დემო როლი, მოთხოვნებს შორის სესიების გამიჯვნა, სტუმრის 401, უფლებების 403 და როლის შეცვლის შემდეგ წვდომის განახლება.

ავტორიზებულ Inertia გვერდებზე, თითოეულზე 5 გასახურებელი და 30 თანმიმდევრული მოთხოვნის პასუხის დროის მედიანა:

| გვერდი | პასუხის დრო |
| --- | ---: |
| მიმოხილვა | 22.96 მს |
| ბინები | 9.53 მს |
| ხელშეკრულებები | 8.62 მს |

ეს ადგილობრივი გაზომვაა დემო მონაცემებზე. ბრაუზერში შემოწმდა დიაპაზონის საზღვრები/გასუფთავება, 320px განლაგება და 3 MiB-ზე დიდი XLSX-ის ატვირთვა/queue დამუშავება. PHP-ის ატვირთვის ზღვარია 5 MiB, POST-ის — 6 MiB; პარამეტრები ინახება `php/frankenphp.d/app.ini`-ში.

## დახარჯული დრო და AI-ის გამოყენება

პროექტზე მუშაობას დაეთმო **5 დღე**, ანალიზის, ფუნქციონალის შემუშავების, ინტერფეისის დახვეწის, ტესტირების, რეფაქტორინგისა და დოკუმენტაციის ჩათვლით.

AI გამოყენებული იყო კოდის ანალიზში, ბექენდისა და ფრონტენდის ფუნქციონალის შემუშავებაში, ტესტების დაწერაში, რეფაქტორინგსა და დოკუმენტაციის მომზადებაში. მიღებული ცვლილებები შემოწმდა ავტომატური ტესტებით, production build-ითა და ბრაუზერში; კონკურენტული ოპერაციები დამატებით შემოწმდა PostgreSQL-ზე.
